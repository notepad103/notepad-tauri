# 名词解释弹窗适用场景和示例设计

## 背景

当前名词解释流程已经支持：对当前笔记生成名词列表，点击名词打开弹窗，流式生成结合文章语境的补充说明，并可继续生成知识图谱或扩展文章。

这次改动聚焦在点击名词后的弹窗体验：新增一个独立区域，用来展示该名词在当前文章语境下的适用场景和示例。

## 目标

- 点击名词后实时生成“适用场景和示例”。
- 在弹窗中用独立区域展示，不混在原始解释或补充说明里。
- 生成扩展文章时，把“适用场景和示例”一起写入文章。
- 暂不改数据库，不保存该区域内容。

## 非目标

- 不做名词卡片管理、复习、收藏或手动编辑。
- 不修改 `note_terms` 表结构。
- 不改变右侧名词列表的生成和保存方式。
- 不新增独立的 AI 请求；沿用点击名词时已有的流式解释请求。

## 方案

后端调整点击名词时使用的补充说明 prompt，让模型返回结构化 Markdown，包含两个二级标题：

```md
## 结合文章的补充说明

...

## 适用场景和示例

...
```

前端保留当前流式接收方式，但在展示层把返回 Markdown 拆成两个区域：

- “结合文章的补充说明”：展示第一个小节内容。
- “适用场景和示例”：展示第二个小节内容。

如果 AI 返回没有严格遵守标题结构，前端采用降级策略：全部内容继续展示在“结合文章的补充说明”，而“适用场景和示例”显示等待或空状态文案。

## 组件和数据流

- `src-tauri/src/ai.rs`
  - 修改 `build_term_supplement_prompt`，要求返回两个固定 Markdown 小节。
  - 保持 `explain_article_term_stream` 的接口不变。

- `src/App.tsx`
  - 继续维护流式文本状态。
  - 新增拆分逻辑，把完整流式文本解析为补充说明和适用场景内容。
  - 生成扩展文章时附带适用场景和示例小节。

- `src/components/TermExplainDialog.tsx`
  - 新增“适用场景和示例”区域。
  - 该区域使用与现有 Markdown 展示一致的渲染方式。

## 状态和错误处理

- 加载状态沿用当前点击名词后的 `loading`。
- 流式生成期间，已有内容可逐步显示。
- 错误状态沿用当前弹窗错误展示。
- 关闭弹窗时沿用当前清理逻辑，清空流式内容和相关状态。

## 测试

- 构建或类型检查应通过。
- 手动验证点击名词后弹窗包含四个区域：
  - 原始解释
  - 结合文章的补充说明
  - 适用场景和示例
  - 知识图谱
- 手动验证“一键生成文章”包含适用场景和示例内容。
